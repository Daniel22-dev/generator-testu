1. HLAVNÍ NÁLEZ A PRVNÍ BLOKUJÍCÍ PROBLÉM
W1 je prakticky reprodukovatelný. Lokální harness spustil skutečný generátor,
vytvořil studentský test a jeho soukromý verifier se syntetickými identitami.
Pomocí veřejného RSA klíče vyrobil nový zašifrovaný payload se správnými
odpověďmi, prázdnými securityEvents, startedAt v roce 2040 a submittedAt
v roce 2000. Importní metadata obsahovala Forms e-mail druhého studenta.
verifyText vrátil classification=current, status=OK, pct=100.

Nejde o získání privátního klíče ani změnu autoritativního skóre: verifier
skóre sám přepočetl ze zvolených odpovědí. Problém je přijetí nedůvěryhodně
vyrobených odpovědí a nekonzistentních metadat jako validního výsledku.
Důvěryhodný Forms e-mail ani čas nebyly v tomto řetězci účinně vynuceny.
Nejsilnější otevřený blok je tedy W1/E3. E1 současně odstraní přímo
opravitelný únik secret-derived dat a veřejný seznam hashů kódů.

Opakované přímé volání verifyText se stejným ciphertextem opět vrací current.
Tento probe nepřidává řádky do RESULTS: sám o sobě neprokazuje dvojí
započtení v UI. Existující agregace umí označit identické duplicity a
vyřazovat je; end-to-end replay a přešifrované podvrhy musí ověřit E3/E8.

2. SKUTEČNÝ RUNTIME FLOW A HRANICE DŮVĚRY
BUILD: assembleTestHtml → varianty s klíči + privátní roster →
assembleSecureOfflinePackage → stripVariantsForStudent → securePublicCfg →
buildSecureStudentHtml. RSA klíčový pár vzniká u učitele. Učitelský verifier
obsahuje privátní RSA JWK a úplné varianty; student má veřejný RSA JWK.
Manifest a SHA-256 hotového student HTML vznikají v generátoru.

STUDENT: secureStudentScript → startTest → RESP + lokální události →
secureAnswers → encryptPayloadForTeacher → SECURE-ANSWERS-V1.
Výsledkový balíček používá hybridní AES-GCM/RSA-OAEP šifrování.
Klientská studentHtmlSha256, startedAt/submittedAt, identita, groupKey,
securityEvents, odpovědi a statistiky změn jsou CLIENT-CONTROLLED.
Upravený runtime může vložit očekávaný hash bez běhu původního HTML.

VERIFIER: verifyText rozbalí a dešifruje → kontroluje testId/manifest a
některé vazby varianty/identity → scorePayload opravuje podle privátního
klíče odpovědí → RESULTS a diagnostika/statistiky.
Shoda testId/manifestHash ověřuje vazbu na známý build, nikoli původ
payloadu. Správné RSA šifrování neprokazuje AUTHENTICITY runtime.

CONFIDENTIALITY: oddělení answer key a privátního klíče je smysluplné.
INTEGRITY: AES-GCM brání změně již hotového ciphertextu bez klíče relace,
ale nezabrání studentovi vytvořit nový platně zašifrovaný obsah.
AUTHENTICITY: veřejný klíč ani klientem hlášený hash ji neprokazují.
CLIENT-SIDE TELEMETRY: prázdný seznam událostí není důkaz nepodvádění.

3. F1–F8 PROTI BASELINE
F1 — STILL PRESENT. Skutečně vygenerované secure student HTML má
ucitelPinHash, recoveryCodeHash a učitelské funkce. Má také dva hashe
šestiznakových studentských kódů v syntetické fixture. Jde o offline

nikoli bezpečnostní hranice. Ostatní teacher/recovery data musí z exportu pryč.

F2 — STILL PRESENT. Studentův self-reported hash může být zkopírován do
podvrhu. Trusted hash uložený ve verifieru nedokazuje jeho skutečné použití.

F3 — STILL PRESENT. Události vytváří studentův prohlížeč. Prázdná telemetrie
s nemožnými časy prošla verifikačním vstupem jako OK. E2 musí opravit
význam diagnostiky; E3 musí kontrolovat sémantiku a externí kotvy.

F4 — PARTIALLY FIXED. Zdroj má HMAC pečetě, revize a sekundární IndexedDB
stav. To zpevňuje běžný reload/rollback téhož profilu. Kompletní restart,
anonymní režim, jiný prohlížeč a úplný reset storage nejsou tímto E0
checkpointem vyhodnoceny jako PASS. Lokální stav nemá globální autoritu.

F5 — STILL PRESENT. Ve veřejné dosažitelné historii byly nalezeny
teacher-derived údaje v osmi HTML blobech; čtyři současné HTML mají hashe
studentských kódů. Ověřené čtyři Pages URL vracely HTTP 200 a bajtově
odpovídaly main. Učitelský verifier ani privátní RSA JWK nebyl při kontrole
nalezen v dosažitelných objektech. To není důkaz absence všech možných
odvozených answer keys ani absence ve všech cache/fork/archive místech.

F6 — STILL PRESENT. rosterForVerifier zahazuje e-mail. Párování Forms
e-mail ↔ kód není v testované cestě vynuceno. Nastavení skutečných Forms
nebylo kontrolováno; povinný checklist je níže.

F7 — STILL PRESENT. Otázky jsou čitelné ve veřejném HTML před startem.
Hybridní šifrování výsledku nešifruje zadání. Povinné šifrování obsahu
AES-GCM + PBKDF2 ze startovního kódu alespoň 40 bitů chybí.

F8 — PARTIALLY FIXED. Existuje diagnostika, auditní události a některé
kontroly duplicit. Chybí úplná odmítací matice E8 a vyhodnocení externích
kotev. Současný probe ukazuje kritickou mezeru, není to E8 acceptance PASS.
